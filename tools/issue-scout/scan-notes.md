# Scan notes

One dated line per change: what I changed in the strategy or rubric, and why.

- **2026-10-16 (strategy, before any scan):** Switched the queries from keywords to org lists. A dry run of "llm" and "agent" with `good first issue` mostly returned tiny personal repos (one account had 24 of 200 results), and search results carry no star count that ranking could use to screen them out.
- **2026-10-16 (strategy):** Split the queries into project families (eval/observability, agent/LLM-app, wider ML) and ran each once per label. GitHub rejects 16 or more owners in one query, and `gh` joins repeated `--label` flags with AND, with no OR form. The third family came from widening my profile to all applied AI/ML.
- **2026-10-16 (strategy):** Added a title rule that drops Windows/JS/TS/Node.js/npm titles. `--language python` matches a repo's main language, not the issue, so the dry run's top 5 still held a Windows-only bug and a JS-package bug that I can't work on from macOS in Python.
- **2026-10-16 (scan 1):** 434 unique results, 138 after ranking, top 5 graded. 1 accept (docling-project/docling-pipelines#306) and 4 rejects, all on `not-claimed`: sktime#11495 and openinference#3785 already had open PRs, rai-toolkit#108 was reserved for a closed PR's author, and docling-pipelines#128 had an open partial PR. Ranking can't see PRs, and "fewest comments first" favours the freshest issues, which are exactly the ones drive-by PRs reach within hours.
- **2026-10-16 (strategy, fix for scan 1):** Added `-- -linked:pr` to all six queries so search drops issues with a PR linked in the Development sidebar. Tested before and after: it drops sktime#11495, openinference#3785 and rai-toolkit#108, and keeps docling#306. docling#128 still gets through because its PR mentions the issue without formally linking it, so that case stays the rubric's job. My first test was invalid: `--` must come last, or `gh` reads every flag after it as search text (exactly 30 results, the default limit, gave it away).
- **2026-10-16 (rubric, `not-claimed`):** Added a fail case: a maintainer comment within 30 days that reserves the work for a named contributor, e.g. asking a closed PR's author to reopen it (rai-toolkit#108). The scout reached the right verdict only by stretching "maintainer-acknowledged claim comment". Regression: Unit 1 harness `--only issue-03,issue-08,issue-09,issue-13,issue-18` (the four claimed rejects, plus issue-09, where the maintainer invited anyone to take a stale claim) agreed 5/5 with gold, and issue-09 still accepts.
- **2026-10-16 (rubric, deliberately unchanged):** docling#306's opener offered "happy to fix it if you assign it to me", with no maintainer reply after a day. My Unit 1 rule still lets it pass (only acknowledged claims block). I kept that rule: the right move is etiquette, asking the opener before claiming, not rejecting the issue.
- **2026-10-16 (site screen, my own mistake):** My first hand screen of the Issue Selection site (2,553 Python issues) used rules stricter than my rubric. It dropped any issue with a claim comment ever posted, any issue not updated in 120 days, any open PR however stale, and every repo outside a 36-repo AI list, which left 29 issues and no good fits. Re-screened with the rubric's own rules (only maintainer-acknowledged claims or reservations from the last 30 days block, only PRs updated in the last 30 days block, repo liveness instead of issue recency, repo primary language Python), it kept 685. The biggest legitimate cut was the 1,420 issues in repos whose primary language isn't Python; the site's Python filter matches any repo that contains Python. Lesson: a pre-filter has to apply the rubric's thresholds, not ones I made up on the spot.
- **2026-10-16 (strategy):** Added a fourth query family, the data/Python infrastructure ML runs on (Apache, Polars, DuckDB, pandas, Dask, Jupyter, marimo, Dagster, Prefect, FastAPI, SQLAlchemy...), plus a matching profile sentence. Tested: 100 results per label, most unassigned. Running all eight queries back to back once hit GitHub's secondary search rate limit (HTTP 403), so a scan may need to pace its searches.

I wrote generic examples rather than quoting cq#393. Why: codex-lb#1467 passed even though gcs8 was pushing a fix on a fork, and I wrongly recommended claiming it.
